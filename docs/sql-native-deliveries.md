# Native monthly email deliveries

**Olbia must feel born in SQL. David Castro is its sole user and owner.** Monthly-close reports and month-end reminders preserve immutable evidence of what Olbia prepared and SES accepted.

`monthly_email_preparations` uses `(delivery_kind, month)` as its personal domain key. Required fields hold owner provenance, preparation time, exact subject/HTML/text and their existing SHA-256. Explicit report-facts/analysis/version/source/error columns preserve original generated evidence; the reminder stores its as-of date. SQL checks constrain the two variants. The JSON facts and analysis prove the historical report, rather than serving as current financial authority. There are no PK/SK/GSI/envelope fields or speculative customer entities.

`monthly_email_receipts` uses the same key and a real preparation FK, with required SES receipt and acceptance time. Both relations are append-only to writer roles. Sent state derives from the receipt relationship. First preparation and first acceptance use native conditional insertion; the worker reuses prepared content and suppresses already-recorded delivery. Every operation shares the existing application SQL client/transaction boundary. Unused product reader roles receive no access to private email content.

SES sending and Scheduler retry/DLQ/alarms remain native provider responsibilities. This conversion preserves the existing external-acceptance ambiguity: SES acceptance and receipt storage cannot commit as one SQL transaction. Racing prepared readers or a crash after provider acceptance may resend. The [SES SendEmail request](https://docs.aws.amazon.com/ses/latest/APIReference/API_SendEmail.html) offers no client idempotency token; this slice does not introduce an outbox/lease subsystem or claim exactly-once delivery.
