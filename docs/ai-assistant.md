# Assistant

Olbia's global financial assistant follows the [UI](ui-design-brief.md) and [financial rules](financial-rules.md). Answers use deterministic tool facts with citations; tools never reconstruct a document-store authority.

## MCP-first interface

The binding [product decision](product-north-star.md#mcp-first-chatgpt-como-interfaz-principal) makes ChatGPT David's primary interface for reading and managing Olbia. One existing Olbia MCP endpoint/OAuth connection serves shared domain capabilities; the web complements it for transaction review, imports and dashboards. Ordinary configuration must not require web interaction. Financial truth, validation, authorization, revisions and audit stay in Olbia; model output never substitutes for them. Financial writes require trusted server-side write authorization and the bounded preview/apply protocol; the existing read scope alone is insufficient.

## Runtime and access

David's 2026-11-17 decision replaces the built-in web chat with ChatGPT as the primary financial interface. The existing CloudFormation `OlbiaChatGptRead` Gateway retains its URL, Cognito client and connector identity; its historical name does not limit it to reads. One OAuth ingress serves the existing read Lambda, a bounded income/goal/manual-charge Lambda and the existing classification Lambda as separate targets. No second MCP server, Gateway, connector or auth proxy is introduced. Cognito authorization code/S256 PKCE, exact owner sub, access-token use, client ID, resource audience and the URL-bound read scope remain required. Native Policy Engine ENFORCE is default-deny: explicit read actions require read scope; registered write actions additionally require the exact URL-bound write scope. Verified JWT claims are native OAuthUser principal tags, with exact space-delimited scope matching; no invented JWT forwarding or model-supplied scope/owner is trusted. See [native OAuth policy semantics](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/example-policies-principal.html) and [reauthorization](operations.md#private-chatgpt-mcp-connection). Read-only grants cannot discover or call write tools. Legacy IAM Gateways/Harness and stored conversations remain intact; monthly-close analysis and ingestion fallback remain independent.

Cognito JWT → dedicated REST API POST /agent/chat → streaming Lambda → AgentCore Harness → IAM Gateways. Ledger's other routes stay on HTTP API. The legacy chat API streams SSE. The web app no longer calls it. Authorizer/handler restrict claims.sub to AgentOwnerSub; tools use the configured AGENT_OWNER, never a model/browser-supplied owner. CORS permits Olbia's web origin, including authorization errors.

Harness owns the loop. Finance read tools and bounded mutations use separate Gateway/Lambda targets. Native Cedar Policy Engine ENFORCE denies by default and permits only the bounded mutation actions to the exact Harness IAM role. Read tools have no write authority; no generic database-write tool or public /bulk-edits endpoint exists. Managed Web Search preserves citations; code interpreter is off.

Harness/Memory/Web Search run in us-east-1; finance Gateway/tools/DSQL in us-east-2. Model/prompt/inference are resolved at runtime, not hardcoded. The Sonnet adaptive-thinking path omits temperature from its invocation and reserves reasoning/answer tokens according to the adapter; provider configuration remains in Prompt Management. Inspect [agent code](../services/api/src/agent) for exact streaming/tool contracts.

The native loop receives the same generation budget as the resolved model, with explicit iteration/time bounds. A limit stop, missing terminal answer or broken stream remains incomplete, closes activity and retains confirmed receipts. Resume in the same conversation. Neither the SDK nor the adapter automatically replays an invocation after failure: a tool may already have committed before the connection was interrupted. Unknown outcomes require reading the operation state before another mutation.

Investment history excludes Cajita/Fondo/debts/Neto. Default period all; as-of uses latest evidence on/before date. Global series carries each account forward and exposes coverage, ages, partial/mixed dates. Variation includes FX and is not flow-adjusted return. Symbol ambiguity returns candidate holding IDs, never guesses. Unit-price extremes exclude pre-buy/post-sell days; extrema use daily evidence even if displayed monthly. Range change and first/last in-range change are distinct. Expected no_data/ambiguous/invalid states are data, technical failures are errors.

`list_movements` paginates with `nextCursor` and stable financial ordering; keep the same period/category/tag filters until the cursor is null. Totals/count cover the complete filter, not one page. Use `_uncategorized` to work through pending classifications; assigning a previous page does not skip the following page. A cursor is a read position, not a persisted snapshot. Each row provides a short `ref`; previews resolve `eventRefs` through native SQL only when each prefix uniquely identifies a movement, then freeze the full IDs. Missing/ambiguous/duplicate references reject without creating a preview; full exact IDs remain available. Never approximate a misspelled ID.

`suggest_movement_classification({movementRef})` accepts an exact UUID or unique short ref for a single charge under review. It returns the current classification and any candidate category or additional tags, with source `rule`, `history` or `haiku`. Only a still-unclassified eligible charge with no decisive rule can invoke Haiku. The model sees the normalized merchant and active catalog. Treat proposals as prompts for David's decision, use the existing category/tag previews and applies for accepted changes, and apply `presupuesto:excluir` only when David explicitly requests the budget effect. If the provider is unavailable or returns no proposal, David can still classify manually.

Gateway handlers return expected domain rejections as `ok=false, status=invalid_request`, with a message and recovery tool; the agent must correct the request instead of retrying it unchanged. SSE marks this as failed activity even if transport succeeded. Unexpected SQL/provider exceptions remain failures. `wealth_snapshot` preserves canonical totals and supplies capture dates/source, missing/stale manual balances, the deterministic Bitso+IBKR subtotal and separate cash/restricted-savings meaning. Its basis is the latest selected snapshots; it does not determine whether a particular recent purchase is included. Never assert absorption or subtract again without evidence; use conditional scenarios when coverage is unknown. A photograph does not establish a month-end forecast, financing terms, zero risk or future income. `month_snapshot` includes known MSI schedules only; the first installment month of a hypothetical purchase remains unknown until established.

### P0 read-only MCP contracts

All four tools share `TOOL_DEFINITIONS`, the finance dispatcher and the existing private OAuth Gateway. Owner comes from configured `AGENT_OWNER`, never tool arguments. Dates/months use America/Chihuahua; monetary fields are integer MXN minor units. These tools neither write financial records nor expose originals, credentials, raw bank evidence or SAT lines. Invalid inputs return the existing Gateway `invalid_request` response; technical read failures remain errors.

- `get_future_commitments({ startMonth? })` returns `getFutureCommitments()` unchanged: currency/currentMonth/generatedAt, 12 `months` with total/MSI/fixed/uncertain minor units, installment counts, comparable changes, fixed source month and individual items, plus `incompletePlans` and optional `nextStartMonth`. Fixed items retain adjusted due days; MSI retains installment index/count/end month. Omit startMonth for the real current month; pass nextStartMonth to continue. The canonical current/future horizon validation, exclusions, reconciliation and inheritance remain authoritative. Scheduling does not prove an unpaid charge, future income or available cash; do not add card liabilities to the schedule.
- `get_month_details({ month })` requires YYYY-MM and projects `getMonthlyPlan()`: `configured`, `incomeMinor`, `depositedMinor`, `estimatedMinor`, `estimateActive`, `provisionalActive`, `provisionalMinor`, `inheritedFromMonth` (or null), concise `payslips` and `upcomingPayments`. `depositedMinor` is recorded CFDI net by payment date; `incomeMinor` can include estimates/provisional liquidity and must not be called a verified deposit. Payslips expose only employerName (nullable), paymentDate, payrollType and netMinor. Each fixed item has ID/name/amountMinor, configuredDueDay and month-adjusted dueDay, reconciliationState (`unlinked`, `linked`, `needs_review`), effectiveReconciliation, linkedMovementId and nullable invalidReason. The effective state comes from the canonical reader; no inferred matching or inherited links. An unlinked item does not establish that a charge is unpaid.
- `get_credit_card_cycles({})` joins active `listCards()` profiles to wealth liabilities by exact card ID. It returns cardId/name/institution (nullable), configuredClosingDay/configuredPaymentDueDay and `outstandingLiability` with amountMxnMinor, snapshotAsOfDay, capturedAt, source, ageDays, carriedForward, stale and freshness. Missing captures yield null amounts and `freshness=missing`; a captured zero remains zero. Manual liabilities become stale at the canonical seven-day threshold. Configured days are profile settings, not actual statement/payment dates. Latest debt is total outstanding including MSI, not a confirmed amount due. actualStatementDate, actualPaymentDueDate, statementBalanceMinor, minimumPaymentMinor, interestFreePaymentMinor and confirmedPaymentMinor are null; installmentMapping is unsupported. Individual-purchase inclusion is not determined, so do not subtract a purchase or scheduled MSI again without evidence.
- `get_wealth_history({ fromMonth?, toMonth? })` accepts YYYY-MM, an ordered inclusive range of at most 24 months. toMonth defaults to the current financial month; fromMonth defaults to 23 months before toMonth. It filters existing `getWealthOverview().history.all` points from `coverageStartMonth=2026-08`; no missing month is synthesized. `months` contains month, asOfDay (historical month-end or today's current-month cutoff), periodStatus (`closed`/`in_progress`), canonical netMxnMinor and nullable components. The history's first-of-month labels are grouping labels: `netObservationDay=null`, not proof of a new snapshot at cutoff. Historical components use `getWealthOverviewsAsOf()`; current components use the current overview. Components are `available` only when their canonical net agrees with the history point; otherwise `unavailable_canonical_history_mismatch` and null, preserving the original net. Available components include canonical asset/liability totals and allowlisted account/card capture facts, with null amounts for missing accounts. `omittedMonths` explains prehistory, absent points and future months; availableFromMonth/availableToMonth are null for empty coverage.

History freshness is evaluated at each asOfDay, not at query time. Each component exposes its actual snapshot day and whether it was carried forward. Derived Fondo has `freshness=payroll_derived_as_of_cutoff`, null capturedAt/ageDays/carriedForward/stale: its synthetic service timestamp is not a bank capture. Market accounts expose age with `age_only_no_staleness_policy`; manual cash/debt use existing stale thresholds. Missing components are not verified zeros even when canonical totals use available balances. History can be partial, preserves canonical coverage limitations and does not interpolate. Net-worth changes are neither spending nor flow-adjusted investment return; debt already includes MSI.

### P1 bounded financial tools

`list_expected_income({fromMonth?,toMonth?,cursor?,limit?})` defaults to twelve months from the current Chihuahua month, maximum 24 inclusive and 50 sources/page. Follow nextCursor. `get_expected_income({incomeId,fromMonth?,toMonth?})` adds the latest 50 immutable change references. Sources expose IDs/revisions, per-occurrence amount/schedule/confidence/status, validity and any confirmed employment termination. Occurrences retain distinct identities, financial dates and overlap status. Actual CFDI net summaries stay separate; no combined actual/expected total is returned. See [accounting rules](financial-rules.md#ingresos-esperados-y-metas-por-mcp).

`preview_income_change({action,...})` supports create/update/archive/restore. Create requires a name, net MXN per occurrence, frequency, start date and confidence. `paymentDays` retains fixed dates (one monthly or two distinct semimonthly days). `paymentRules` accepts `{kind:"calendar_day",day}`, `{kind:"previous_business_day",day}` and `{kind:"last_business_day"}`. A one-time source uses `expectedPaymentDate`. Business-day schedules leave partial employment months unknown. Fixed schedules can opt in with `withholdPartialMonths:true`. `monthOverride:{month,reason,paymentDate?,amountMxnMinor?,confidence?}` replaces a month for that source. Omitted amount means unknown. An explicit zero without a date means no expected payment. `clearMonthOverride` takes the month to remove. Updates require `incomeId` and `expectedRevision` from a recent read. Preview shows the before/after and affected dates. `apply_income_change({operationId})` revalidates the revision, payroll evidence and calendar version before committing. Preserve null amounts and provisional calendar labels in explanations. See the [financial rules](financial-rules.md#ingresos-esperados-y-metas-por-mcp).

`list_financial_goals({status?,cursor?,limit?})` returns up to ten goals/page with totals, allocations, payments and nextCursor. `get_financial_goal({goalId})` adds the latest 50 change references. Amounts and outstanding commitments come from shared deterministic domain calculations; all money is integer MXN minor units. Original and amended budgets stay distinct. Payment references are IDs, never raw evidence. A manual attestation is not a bank confirmation; changed or uncertain linked evidence remains visible.

`preview_financial_goal_change({action,...})` supports create_goal, update_goal, archive_goal, add_allocation, update_allocation, archive_allocation, record_payment, correct_payment and void_payment. All edits require goalId/expectedRevision; affected allocations/payments require their exact revisions. create_goal accepts allocations atomically; update_goal accepts multiple existing allocation changes and an explicit budget amendment in the same transaction. clearTargetDate/clearExpectedPaymentDate remove optional dates. Payment input requires amountMxnMinor, paymentDate and explicit source, plus ledgerMovementId for linked evidence. Correction/void requires reason; no original assertion is deleted. `apply_financial_goal_change({operationId})` revalidates the whole captured aggregate and linked evidence before committing.

`preview_manual_charge({institution,merchantRaw,amountMinor,currency?,occurredOn,accountLastFour?,note?})` is **Registrar cobro** through the existing manual-entry service. Preview shows the exact observed input, existing idempotent capture if any and canonical automatic Amex MSI behavior; no business row or original is written during preview. `apply_manual_charge({operationId})` stores the original outside SQL retry callbacks, then commits canonical movement/observation/source claim and immutable operation receipt together. Responses allowlist movement facts and MSI terms; no raw observations, evidence pointers or credentials. Use list_movements for a fresh read.

For an observed installment, read `get_msi_reconciliation` and call `preview_manual_reconciliation` with `action: installment`, the movement ID, installment index, literal amount and date, and the source of evidence. The preview uses the current calendar and expires after fifteen minutes. Apply the authorized operation ID and use `get_financial_write_status` after interruptions. The operation can also create a movement or first installment, attach evidence to an existing movement, or preview reversal. A later import can verify the same installment. Reversal requires that the evidence and its financial effects still be current.

`preview_manual_credit` takes `creditType`, `institution`, `accountKind`, `accountLastFour`, `amountMinor`, `postedOn`, `description`, `evidenceReference` and `confirmedPosted:true` from an actual bank credit. Income requires cash and `incomeType` of `finiquito`, `nomina` or `otro`. Refunds to a credit card are distinct from cash refunds. A `card_payment` requires a credit card and remains separate from cash income, refunds and spending. A `fund_release` uses the existing `fundEmployerKey` from `month_snapshot` and compares the bank amount/date with the immutable payroll fund closure. Keep the fund outside ordinary income and captured cash. `apply_manual_credit({operationId})` commits one native credit, evidence and an immutable receipt. Exact retry returns the same credit, and conflicting facts for that institution/reference require review. Use `month_snapshot` for the bank posting month. Leave predicted payroll or promised refunds unrecorded.

In `month_snapshot` and the web dashboard, `spending` exposes registered, budget-counted and estimated closing spend independently of payroll. `postedCredits` describes recorded inflows and refunds. `futureIncome` describes schedule certainty. `cash.current` is the dated snapshot and `cash.closing` provides the recorded historical close or specific reasons for unavailable cash estimates. The legacy payroll block `liquidity` has `statusBasis:payroll_only`. Never add CFDI, fund payouts or posted credits to the cash balances by inference, and never subtract purchases and their card settlements as separate cash expenses.

`get_financial_write_status({operationId})` returns pending/applied/failed/expired (or owned not_found), type/action, expiry, persisted immutable result and recovery guidance. Applied receipts prove that historical operation, not an unchanged current record. An interrupted apply must reuse the same authentic operation after reading status; failures/conflicts/expiration require a fresh preview. A fully explicit user instruction authorizes preview and apply in the same conversation. Never invent missing schedule, amounts, IDs, revisions or payment attestations. Preview expires after fifteen minutes and changes no current financial entity. Apply is idempotent and atomic with the receipt. Payroll/wealth stay untouched by expected income or goal configuration.

Extension points: `financial-tool-definitions.ts` owns financial read/write registrations; `financial-write-tools.ts` dispatches bounded operations into shared domain services. Infrastructure `McpBoundedWriteTarget` registers a target/definitions under the same Gateway; `mcpToolPolicy` generates exact-scope permits from those definitions. A future tool uses its typed domain/repository, bounded service and least-privilege role, then joins a registered target; it must not create new authentication plumbing, broaden read authority or turn preview history into a generic document store. Existing classification preview/apply/undo/manage_category services are exposed through the scoped classification target without changing their established contracts. Their recovery tool remains edit_operation_status.

This release prioritizes backend/MCP. Shared authenticated REST reads and preview/apply/status endpoints expose the same income/goals service for the complementary web app; additional app UI is deferred. No personal example financial records are seeded during deployment.

## Mutations

An explicit chat instruction authorizes the bounded tags/category change. In the same turn:

1. Resolve exact movement IDs or inclusive date range plus explicit selector. Tags accepts exact merchantRaw/sourceTags/onlyUntagged; categories merchantRaw/sourceCategoryId/onlyUncategorized. Dates alone are rejected. Only accepted movements are eligible.
2. Preview returns every affected movement and freezes IDs, previous/next values, count and amount. Maximum 49 movements per operation; batch accepts 1–12 nonoverlapping operations under existing limits.
3. Apply exactly those operation IDs atomically, creating a revision per movement. Changed preconditions/expired previews reject apply and require a fresh preview. Apply/undo are idempotent; undo restores frozen before-state under current preconditions.
4. SSE mutation refreshes ledger and shows factual receipt per operation. No second UI confirmation; undo is requested by chat. Category edits never change merchant rules. Tags never change financial totals.

### Category catalog control plane

An explicit instruction such as “crea Mascotas” or “renombra Shopping a Compras” authorizes `manage_category` in the same turn, without a second UI confirmation. `list_categories` returns all SQL identities, including archived entries, their revision and a fresh operationId. Create requires a new stable ID and name; update requires the current revision and changes only name/order. An existing ID never changes.

Archive is the catalog deletion operation: it retains the identity, historical labels, movement references and merchant rules, blocks new assignments and suspends automatic matching to that category. Restore reactivates it. Undo of a prior movement assignment may restore an archived historical category; new apply operations must target active categories. Renaming changes the displayed label in historical views while retaining the category ID and every earlier catalog value in immutable history. Catalog edits do not reclassify movements or create merchant rules; use the existing bounded movement tools when David also requests assignments.

Catalog changes commit atomically with lifecycle revision and immutable before/after history. The same operationId and arguments return the original receipt; reuse for another request or a stale revision fails. Legacy catalog PUT participates in the same history/revision and cannot reactivate archived entries. SSE emits a factual catalog receipt and refreshes affected views and assignment choices. To revert, read the latest revision and apply the previous name/order or archive/restore in a new audited operation. No generic SQL write tool is exposed.

## Conversations and memory

AgentCore Memory owns raw transcript/discovery and 365-day retention; durable facts/preferences are separate. SQL conversation_threads stores original title/first month/activity/expiry; assistant_thread_selection stores David's active choice with FK. Listing intersects metadata with provider HAS_EVENTS and can backfill visible older sessions. Eventless headers are not invented history or grounds for destructive cleanup.

Closing sheet/reloading/changing month keeps session; month supplies next-turn context. New Conversation clears active choice without deleting old threads. GET /agent/threads lists recent conversations; detail restores visible provider events; PUT /agent/threads/active selects/clears; DELETE removes provider events before atomic metadata/selection cleanup. Provider failure preserves metadata; provider and SQL deletion are not one transaction. Scheduled metadata expiry is separate from provider retention.

Memories never mutate ledger/totals. Long-term strategies reject assistant inference, intermediate calculations, current balances and unconfirmed units/dates; explicit user correction replaces prior fact. Keep conversations and durable memories independently visible/deletable. Private mode protects restored text/titles/receipts. Show citations and compact tool status/duration, never raw financial inputs, private reasoning text/signatures or restored activity as live. Failed tools remain visibly unavailable while other results may support a partial answer.

## Prompt Management

**Binding:** private prompt, profile and voice live exclusively in Bedrock Prompt Management. Never commit them or add application seeds/default/fallback prompts or model/inference defaults. Active pointer: SSM /personal-finance-v1/agent/runtime-system-prompt-version-arn → immutable version ARN. Runtime reads it with ~30-second cache, GetPrompt and Harness overrides. Required version: nonempty text/system prompt, modelId, temperature and maxTokens configuration. CDK owns retained AWS::Bedrock::Prompt; CI preserves current DRAFT through NoEcho parameters, without storing private content in Git. Deploys do not promote versions or change pointer.

Before creating/promoting a version, read active version and latest personal-profile baseline; merge new behavior without losing profile, voice or retained operational rules. Baseline v10 preserves v5's private profile plus continuity/investment/research behavior; only an explicitly approved successor replaces it. Verify all preserved sections before version creation and again by reading back immutable version; only then move SSM pointer. Never substitute generic v9/profile-less text. Rollback selects a verified prior immutable version. These are authorized runtime prompt operations, separate from code deployment; verify AWS identity as in [operations](operations.md).

Monthly-close analysis reads only private profile/voice from that same version, excluding chat tool rules and prompt text from persisted reports. [Agent runtime README](../services/api/src/agent/README.md) points here for enforcement and to deterministic scenario/golden tests for validation.

## Monthly spending budgets

`month_snapshot({month})` and authenticated web `GET /agent/month-snapshot?month=YYYY-MM` return the same monthly snapshot from the shared SQL reader. Use `budget` for counted spend, known commitments, signed margin, thresholds and category limits. Its `spendTimeline.cumulativeMinorByDay` starts at index 0 and stops at the financial cutoff. Spend without a plottable day is included in the total and disclosed separately. Use `liquidity` to distinguish recorded, estimated, provisional and missing liquidity and use its nullable current-month projection. Amounts are MXN minor units.

`list_budgets` returns recurring versions and monthly overrides, including archived configurations, typed allocations, IDs/revisions and pagination. `get_budget_status({month?})` resolves the effective configuration and returns gross/counting spend, category limits, unallocated budget, remaining discretionary amount after known fixed/MSI commitments, pace, elapsed percentage, 70/90/100 warnings and daily allowance. It includes explicit exclusions and incomplete-data warnings. `get_budget_history({fromMonth,toMonth})` compares up to twelve inclusive months and includes the latest fifty owner-budget change references. `simulate_budget_purchase({month?,amountMxnMinor,categoryId?})` is read-only and assumes an additional counted MXN purchase; it never infers MSI or changes financial records. These are shared SQL-backed REST/domain services, not MCP calculations.

`preview_budget_change` / `apply_budget_change` extend the existing financial write target, exact write-scope policy, fifteen-minute preview, status recovery and immutable receipts. Supported actions: set_recurring, set_override, reallocate, archive, restore, exclude_movement and include_movement. New configuration requires month and totalMxnMinor; allocations is the complete intended list. Updating requires entityId/expectedRevision from a fresh read. An inherited recurring configuration can be changed, archived or restored with an explicit later month: the service creates a new version, preserving its source and revalidating it at apply. Overrides apply only to their month. Reallocation requires fromCategoryId, toCategoryId and amountMxnMinor and preserves the total. Category sums cannot exceed total; unallocated remains explicit. Exclusion/inclusion requires an explicit reason and exact movement/month or exclusion ID/revision. Adding or removing `presupuesto:excluir` uses the existing tag edit tools and takes effect in budget reads without a budget write. Active manual exclusions still apply for their month. See `tagExcludedMovementIds` for movements excluded solely by tag. Recurring changes cannot rewrite closed months; explicit historical month overrides/exclusions remain auditable. See the canonical [budget financial rules](financial-rules.md#presupuestos-mensuales-por-mcp).

Authenticated REST exposes GET /budgets, /budgets/status and /budgets/history, POST /budgets/simulate and /budgets/preview, plus the existing financial-writes apply/status routes. Web budgeting controls are deferred; every operation is available through the single ChatGPT connection. Refresh tools after deployment to discover the new tools; existing write authorization remains required. Deployment verification rolls back all test budgets and receipts without seeding personal budgets.

### Configuración de gastos fijos

`list_fixed_expenses({month})` devuelve los IDs, revisiones, configuración recurrente, ajustes mensuales, ocurrencias y vínculos del mes. Usa el mes de vigencia exacto para obtener `expectedRevision`. `preview_fixed_expense_change` requiere `action`, `scope`, `month` y `reason`. Usa `create`, `update`, `archive`, `restore` o `clear_override`. El alcance es `recurring` o `month`. El alta requiere nombre, importe en centavos MXN y día de pago. Para cambios usa `paymentId` y la revisión de la lectura. `nextEffectiveMonth` identifica una versión recurrente posterior que conserva su vigencia.

`apply_fixed_expense_change` usa el ID auténtico del preview y el permiso de escritura vigente. Ante interrupción consulta `get_financial_write_status` con el mismo ID. Confirma programación con `list_fixed_expenses` y presupuesto con `get_budget_status`. La web usa los mismos servicios por `GET /fixed-expenses`, `POST /fixed-expenses/preview` y las rutas compartidas de aplicación y estado. [Reglas financieras de gastos fijos](financial-rules.md#nómina-y-gastos-fijos).

### Conciliación desde MCP

- `preview_fixed_reconciliation` / `apply_fixed_reconciliation` vinculan o desvinculan una ocurrencia mensual. Lee `get_month_details` para el ID, vínculo actual y programación original, incluido `configuredDueDay`. Identifica el cargo con `list_movements`. Conserva el importe observado, la programación y sus decisiones inmutables.
- `get_msi_reconciliation({month,movementId?,merchant?,limit?,offset?})` devuelve el plan vigente, su `expectedRevision` y referencias de filas bancarias aplicadas sin publicar originales. Consulta por ID para una compra sin plan. `preview_msi_reconciliation` / `apply_msi_reconciliation` confirman o corrigen una cuota en el calendario compatible. `correct_schedule` exige principal, cuota e índice/plazo impresos y no mueve cuotas registradas o canceladas. Mantiene la compra y el vínculo de evidencia.
- Preview y apply usan el target de escritura existente. Apply revalida estado y evidencia, confirma con recibo en una transacción y devuelve el mismo recibo al repetir el ID. Ante interrupción consulta `get_financial_write_status` y verifica los totales con `month_snapshot`.
