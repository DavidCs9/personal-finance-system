## Decisions

### D1 — Normalize import captures before constraining core provenance

- Context: MSI currently labels parsed row identities as observation IDs; repeated imports preserve the same row identity and frozen candidate decisions. A global observation/row UNIQUE or FK would corrupt historical semantics.
- Evidence and uncertainty: Fresh data has 484 parsed rows across 15 retained files, including five repeated MSI identities and two legacy backfill markers. Actual source targets for two Amex claims no longer exist, with no retained revision proving the reason. Original evidence and applied/preview classifications survive.
- Alternatives: Fold all imports into a single oversized ledger rewrite; impose uniqueness on raw identities; preserve operational row arrays; or normalize each import capture with ordered children first and keep historical decision references distinct from canonical relationships.
- Decision and reason: Choose native import kind/content hash and ordered per-import row identities. Normalize candidate snapshots as children when implementing; retain historical candidate labels and selection IDs as evidence rather than joining them to current merchant/category values. Do not invent a current movement FK for a frozen candidate assertion. Resolve exact MSI provenance separately against these native captures in the core slice. This establishes real relational parents without recreating document routing.
- Consequences and verification: Preserve every source field, row, order and optional-field distinction; verify repeated identities and original files independently. No global uniqueness on a statement identity or automatic suppression deletion. Complete all import lifecycle readers/writers before promoting the domain.
- Status: Decided before implementation; native schema and lifecycle design remain next.

### D2 — Guard the header and make apply rollback as one domain operation

- Context: Statement/CSV apply currently commits financial rows/claims separately before recording final import status. A late old runtime after native copy could mutate financial records then fail the frozen header update, leaving an apparently unapplied operation.
- Evidence and uncertainty: Both statement providers share applyStatementImport; CSV has its own loop. Individual row transactions are already atomic, but the complete loop/header lacks an outer transaction. All live imports are modest in size; an oversized transaction must fail with all SQL changes rolled back, not chunk partial financial decisions.
- Alternatives: Guard only the last header mutation; dual-write import forms; pause all writes; or stage an import-family marker guard and use the existing native application transaction/barrier around complete apply loops.
- Decision and reason: Before native migration 13, block legacy import-family Put/Update/Delete once its marker exists and wrap shared statement apply plus CSV apply in the existing application transaction. A marker change conflicts with the same barrier; all financial rows, observations, claims, revisions and final header commit or rollback together. Unrelated domains/claim families continue normally. Preserve Amex's existing optional post-apply deferral behavior separately; this guard does not redefine that product behavior.
- Consequences and verification: Test all provider families and mutation forms, retained reads, marker interruption, unrelated writes, sequential row writes followed by blocked completion, and actual statement/CSV apply rollback/retry. Frozen header rejection must roll back earlier SQL changes, with no command receipt left behind. Native implementation must respect DSQL's transaction row limit; no partial-receipt workaround.
- Status: Decided before implementation. Guard preparation begins only after recording this decision.

### D3 — Native capture keys, signed rows and candidate evidence

- Context: Import headers mix provider workflow with document routing, and parsed rows/candidate arrays are duplicated operational JSON. Candidates are frozen reconciliation assertions, not today's movement relationships. The existing one matched MSI row has a target ID without a candidate label.
- Evidence and uncertainty: All 15 kind/content hashes match original evidence; all 484 row identities are unique within their import, while identities repeat across files. Candidate arrays contain 39 unique-in-row IDs and 38 labels, preserving the same relative order. All amounts are safe integers, including four negative credit rows. Statement MSI flags match row kind; a credit flag is a separate bank assertion and cannot be inferred from signed amounts. CSV creation uses previewedAt; PDF creation uses createdAt.
- Alternatives: Retain operational rows JSON; create new random identities for each backfill; globally deduplicate assertions from different files; or typed capture/row/candidate tables with native composite keys and restrictive FKs.
- Decision and reason: Use `bank_imports(kind,content_sha256)` for the personal import identity, with typed owner/lifecycle/timestamps/account label/period/evidence/extraction job/error and applied result counts. Require the original creation time (CSV's first preview time is its creation), preserve a separate known preview timestamp, and retain variable Textract answers as extraction evidence JSON. Use `bank_import_rows(kind,content_sha256,position)` with native parent FK, unique identity within capture, signed safe MXN amount, calendar date/merchant/status, optional statement kind/credit, installment assertions, CSV row/occurrence/transaction ID and frozen selected target ID. Derive statement MSI from row kind. Use ordered candidate children with native row FK, unique target per row and nullable historical merchant/time label; absent label remains distinct from a labeled candidate. Do not FK a historical candidate ID to today's mutable ledger.
- Consequences and verification: Native checks cover required identities, enums, safe signed money, calendar dates and positions. Initial copy is 15 headers + 484 rows + 39 candidate children + barrier/marker = 540 mutations, below DSQL's 3,000-row limit. Validate known field sets, candidate shape/order and source identity before atomic copy; fail closed on unrepresentable data. Preserve all 38 labels and the unlabeled target. Public arrays remain response shapes only. Use native PK access for point lookups, not a speculative index. [Native constraint syntax](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/create-table-syntax-support.html) and [transaction limits](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/CHAP_quotas.html) were checked before choosing the design.
- Status: Decided before implementation; exact SQL decoding/private preflight, native schema and service tests are next.

### D4 — Keep applied capture decisions stable on repeated upload/apply

- Context: Statement apply already returns its retained result after application; CSV reapplies and can overwrite the original result with a duplicate-only summary. Re-uploading an already applied hash can also reset its lifecycle and candidate assertions.
- Evidence and uncertainty: Every existing applied capture has a result summary and original file hash. The app has no explicit unapply/reprocess operation. A new preview of a pending file can legitimately refresh candidates; an applied capture is historical financial evidence. Claim suppression remains the financial row idempotence mechanism until core normalization.
- Alternatives: Preserve accidental applied-result rewriting; invent a versioned reprocess product flow; or use the native import identity to return the existing applied capture without resetting it, while allowing explicit upload to refresh pending/failed workflows.
- Decision and reason: Preserve applied capture rows/candidates/result, and make every provider apply return its retained summary when already applied. Repeated upload of an applied hash returns its existing terminal result. Pending/failed uploads may refresh workflow/candidates under the native barrier; native mutations must check current state so late polling cannot overwrite an applied capture. No new reprocess UI or generic workflow framework.
- Consequences and verification: Test duplicate and concurrent apply/upload, late poll after apply, pending refresh, failed retry, initial copy replay and immutable applied evidence. Native apply retains the guard's whole financial transaction. Reject over-budget child replacement before relational mutation; never chunk an import into competing partial authorities.
- Status: Decided before implementation.

### D5 — Preserve extraction evidence under late concurrent polling

- Context: Guarding the SQL lifecycle alone cannot stop a late poll from overwriting the shared `.textract.json` S3 key after another job's preview has been applied.
- Evidence and uncertainty: Existing original objects are retained and freshly verified. New processing retries can have a different Textract job ID, and concurrent polls of the same job can finish after application. [S3 natively supports conditional creation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html) with `IfNoneMatch: '*'`.
- Alternatives: Keep overwriting one extraction key; build a custom evidence lock/version framework; or use immutable, job-specific extraction objects with S3 conditional creation and explicit SQL evidence pointers.
- Decision and reason: Preserve all historical keys unchanged. New extraction keys include the SHA-256 of the Textract job ID and use native conditional creation. A precondition failure means that same job already has its retained extraction; other failures propagate. Parse the retained object so a competing first writer's evidence and the chosen preview always agree. SQL preview completion checks the expected job and returns current state when stale. Keep SQL completion outside the parsing-failure catch so storage errors cannot become misleading parser failures.
- Consequences and verification: Test repeated and late polling, failed retries, applied uploads, native SQL failures and S3 conditional creation. Original PDFs/CSVs stay content-addressed. No custom locking or telemetry is added.
- Status: Decided before implementation.

### D6 — Native Textract start idempotence and expired-job recovery

- Context: Concurrent first uploads can both start external OCR before either SQL header commits. Also, returning the current processing capture on repeated upload must not strand an expired provider job forever.
- Evidence and uncertainty: [Textract's native ClientRequestToken](https://docs.aws.amazon.com/textract/latest/dg/api-async.html) reuses one job for identical start requests for seven days; job results expire after seven days. Provider InvalidJobIdException explicitly identifies an unusable job. Transient provider/storage failures do not prove the document is bad.
- Alternatives: Add an external-job lock/queue, launch duplicate jobs, or use the native token plus existing failed/retry lifecycle.
- Decision and reason: Hash provider, evidence bucket/key and the prior job ID (or initial marker) into a native start token. Concurrent starts/retries observing the same prior state use the same token; a failed retry uses a new token. Convert an invalid/expired provider job to an actionable document error and conditionally mark only that current job failed, allowing explicit re-upload to retry. Leave unrelated provider failures processing and retryable.
- Consequences and verification: Test stable initial tokens, distinct retry tokens, provider error discrimination and expired processing retry. No custom job lock, background workflow or extra database state is introduced.
- Status: Decided before implementation.
