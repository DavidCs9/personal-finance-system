The [completed run](autonomous-runs/2026-10-02-native-payroll.md) preserves exact receipt/line, immutable-source, role/index and rolled-back smoke acceptance. Olbia must feel born in SQL. `payslips` uses the actual CFDI UUID as its native UUID primary key; `payslip_lines` uses `(payslip_uuid,position)` with a native FK. Receipt fields hold payment/pay-period dates, payroll type, source MXN totals, employer, ingestion time and explicit XML evidence coordinates/hash/content type. Lines hold SAT kind/type/code/concept and safe nonnegative MXN amount. Every original line retains its order, including zero-value lines and repeated SAT descriptions.

Month is derived from the payment date. Line group and the employer Fondo noncash flag are derived from SAT kind/type using the existing domain rules. Currency is expressed by MXN amount columns and the existing payroll contract. No duplicate operational month, currency, classification, line array, document keys, command envelopes or whole-document JSON remains. Native date-range reads LEFT JOIN ordered lines in one statement; receipts with no lines remain visible. Public UUIDs stay uppercase and optional-field behavior is preserved. Calendar dates are returned as SQL text, avoiding driver timezone conversions.

## Imports, immutable evidence and money

A native UUID preflight avoids uploading evidence again for an existing receipt. XML still uploads to the existing S3 evidence bucket, with the original content hash and deterministic key. Receipt insertion uses `ON CONFLICT DO NOTHING RETURNING uuid`; ordered children insert in the same existing application transaction/barrier. Concurrent preflights may both see absence, but native UUID uniqueness and the shared barrier select one complete receipt. The losing attempt returns duplicate. No duplicate import changes the original date, amount, source or lines. S3 upload remains outside the SQL transaction as before; an interrupted/conflicting attempt may retain an unreferenced evidence object, while no partial financial receipt commits.

Application/cutover grants on receipts and lines permit SELECT/INSERT only. Product code cannot overwrite or delete immutable payroll evidence. Native PK/FK/CHECKs enforce identity, membership, SAT kind/type and nonnegative safe-integer money. Source totals are retained assertions, even where line sums reproduce them; derived income/Fondo/compensation are not competing stored balances.

DSQL permits 3,000 mutated rows in a transaction. At most 2,998 lines reserve one receipt and one application barrier row; positions 0–2997 enforce the same bound natively. An oversized new receipt fails before evidence upload/storage, preserving atomicity. The initial real-data copy has 19 receipts and 192 lines, including 19 zero lines and 18 noncash employer Fondo lines. A single parameterized SQL recordset insertion uses JSON only as transient bulk transport; no array or JSON value is persisted in the native tables.

## Cutover and recovery

Guard [#181](https://github.com/DavidCs9/personal-finance-system/pull/181) is deployed and independently accepted. It rejects every legacy payroll or CFDI-specific claim mutation after marker 12, leaving unrelated claim families operational. The old upload wrote both halves under the shared application barrier, so it commits before native copy or retries into maintenance afterward.

Native bootstrap creates constrained tables separately, then uses the official connector’s retrying transaction to update the barrier, validate retained list/classification/claim membership and transaction budget, copy every receipt and ordered line, and record marker 12 together. Failed/interrupted copying rolls everything back. Replay skips the copy after marker 12, preserving later native receipts. A native payment-date index is created asynchronously and awaited before enabling consumers/grants. CloudFormation dependencies order every new runtime after bootstrap. Brief payroll-upload maintenance during replacement is the staged cutover tradeoff.

Frozen `payroll`, CFDI claim documents and checkpoints remain separately verified migration/recovery evidence. They do not receive new uploads or act as a fallback. All month/year/detail reads, income/provisional/twin derivation, compensation, Fondo/Patrimonio, reports and workers use current native payroll. Obsolete payroll readers, document commands and `DSQL_PLANNING_READ_MODE` are removed. SQL errors propagate.
